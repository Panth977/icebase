IceBase · Phase 1 API cut

ORCH-26 · approved by Panth 2026-10-24 · from PRD rev 8 §10 + Panth's 2026-10-24 list. Only the APIs nearly every Firebase app calls; everything else waits for phase 4+.

~170APIs kept in phase 1 (of 1,054)
6services: app, auth, firestore, RTDB, storage, hosting
15new management APIs (create db / schema / rules from code)
yesfunctions: minimum set (onCall, onRequest, doc triggers, onSchedule)

Decisions (Panth, 2026-10-24)

  • API cut: approved as drafted.
  • Cloud Functions: in, the minimum set below.
  • Modes in phase 1: firebase + emulator (SQLite) together. vm mode stays phase 3.
  • Console GUI: after the SDK + CLI work.
  • License: Apache-2.0.
  • Auth: no vendor lock-in even in firebase mode — custom email / phone / Google OAuth flows with your own senders. See custom-auth.html.
  • Firebase test project: the build may create one for e2e.

How to read this

  • Client = icebase/<svc> (mirrors firebase/<svc>). Admin = icebase/admin (mirrors firebase-admin).
  • Manage new = IceBase-only, lets code do what the Firebase console GUI does. In firebase mode they call Google's management REST APIs with the service account; in emulator/vm they act on the IceBase server.
  • Same names, same argument shapes as Firebase. Typed from the schema (PRD §6, §9).
  • Cut later = exists in Firebase, deliberately not in phase 1.

Around the APIs (phase 1, from the PRD)

  • Schema runtime validation on every write; typed reads (SCH-1/2).
  • Composite-index check at compile time (MissingCompositeIndex) and at runtime (IDX-1/2).
  • CLI: icebase init, icebase deploy --env X, icebase indexes check.
  • Console: after the SDK + CLI work (Panth).
