1. Summary

IceBase is a Firebase wrapper with every Firebase API, which lets you move from Firebase to your own VM.
It runs in three modes: firebase (default), emulator (SQLite, local) and vm (self-hosted, Postgres). You pick the mode per service. One console GUI covers all modes. Data has an explicit schema and declared composite indexes. Queries are type-safe in frontend and backend. Rules are Firebase rules.

Problem

  • Firebase gets expensive as usage grows, and leaving means rewriting the app: there's no drop-in self-hosted Firebase.
  • The Firebase emulator doesn't enforce indexes, so missing-index bugs only show up in production.
  • Firestore is schemaless and untyped. Typos in field names and wrong value types reach the database.
  • Developers learn three tools: Firebase console, emulator UI and whatever runs on a VM.

Solution in one paragraph

Apps import icebase/* instead of firebase/*. The function names and call shapes are Firebase's. A single icebase.config.ts declares the schema (collections, fields, composite indexes), the rules files, functions, hosting, and, per environment, which mode each service runs in. In firebase mode IceBase calls the real Firebase SDKs and adds type checks and index checks. In emulator mode a local IceBase server implements the same APIs on SQLite. In vm mode the same server runs as one Docker image on Postgres. The IceBase console manages all three.

2. Goals & non-goals

Goals

  • G1 Same API surface as Firebase (names, arguments, results) for every service in scope.
  • G2 Explicit schema for documents, function inputs/outputs and claims; typed autocomplete in frontend and backend.
  • G3 Composite indexes are declared; a query that needs an undeclared composite fails at compile time where possible, and always at runtime in every mode.
  • G4 Firebase rules syntax enforced identically in all modes.
  • G5 Emulator mode replaces the Firebase emulator and enforces indexes; it handles millions of documents for development.
  • G6 VM mode: one Docker image on one port, Postgres underneath, parallel transactions, aimed at a ~$100/month VM.
  • G7 Mode chosen per service per environment (e.g. Firestore on Firebase, functions on the VM).
  • G8 One console GUI for all modes.
  • G9 Move a service's data between modes with one command.

Non-goals

  • Wire compatibility with Google's SDKs talking to the IceBase server (apps use icebase/*).
  • Self-hosting push delivery, SMS, Google Analytics data, Gemini models (these stay external).
  • Mobile-only Firebase products (Crashlytics, In-App Messaging, App Distribution, Test Lab client, Dynamic Links).
  • Multi-region / HA clustering in VM mode (single box + backups).
  • Databases other than SQLite (emulator) and Postgres (VM).
  • Schema-less writes (every collection must be declared).

4. Product principles

  1. Firebase names, Firebase behaviour. If Firebase has getDocs(query(...)), IceBase has exactly that. No new query language.
  2. Explicit beats implicit. Schema and composite indexes are declared in code and reviewed in PRs.
  3. Fail early. Compile time first, then runtime with a clear message naming the missing index, in every mode.
  4. One config, many places. icebase.config.ts is the only source of truth; Firebase index files, SQL tables and RTDB .indexOn are generated from it.
  5. Per-service freedom. Each service picks its mode independently.
  6. One console. The GUI doesn't change between modes.

Per-service mixing

Each environment sets a default mode; any service can override it. Requirements:

  • MIX-1 Services in the VM accept Firebase Auth ID tokens (verified with Google's public keys) when auth runs on Firebase.
  • MIX-2 Functions on the VM can be triggered by Firestore on Firebase (listener bridge; per-document ordering, at-least-once).
  • MIX-3 Functions on Firebase can be triggered by documents on the VM (signed webhook to the HTTPS function).
  • MIX-4 icebase drivers --env X prints the wiring and refuses impossible combinations at deploy time.

Known hard limits: Firebase Hosting can't rewrite to functions on the VM; Firebase Storage rules can't read documents stored on the VM. Native auth + Firestore on Firebase needs a token bridge (custom tokens).

6. Schema

Every collection (and RTDB path) is declared in TypeScript. The schema drives types, runtime validation, generated index files, SQL tables and console forms.

import { collection, f } from 'icebase/schema';

export const products = collection('products', {
  fields: {
    name: f.string(),
    priceCents: f.number({ int: true, min: 0 }),
    category: f.enum(['shoes', 'shirts', 'bags']),
    tags: f.array(f.string()),
    stock: f.number({ int: true }),
    active: f.boolean(),
  },
  indexes: [
    ['category', 'priceCents asc'],
    ['tags contains', 'priceCents asc'],
    ['active', 'stock desc'],
  ],
});

Requirements

  • SCH-1 Writes are type-checked at compile time and validated at runtime (all modes) before being sent; invalid writes fail with the field path and expected type.
  • SCH-2 Reads return typed data. Documents that don't match the schema (legacy data) are returned with a warning in dev and counted in the console's "schema drift" view.
  • SCH-3 Subcollections use path templates (users/{uid}/orders); the params are required arguments.
  • SCH-4 Schema changes: adding optional fields and new collections is free; adding required fields, renaming or narrowing types needs a migration script (icebase migrate), checked by icebase deploy.
  • SCH-5 noIndex per field mirrors Firebase single-field exemptions; ttl marks a TTL field.
  • SCH-6 Function inputs/outputs, auth custom claims, Remote Config parameters and RTDB paths use the same DSL.

7. Indexes

Firebase indexes every single field automatically. IceBase keeps that: any query on one field works without a declaration. Queries that need a composite index only work when it's declared in the schema.

QueryComposite needed?
where('name','==','Boot') (any field)no
orderBy('stock','desc')no
where('priceCents','>',1000), orderBy('priceCents') (same field)no
where('category','==',x), where('active','==',true) (equality only)no (Firebase merges single-field indexes)
where('category','==',x), orderBy('priceCents')yes: category + priceCents
where('tags','array-contains',t), orderBy('priceCents')yes: tags contains + priceCents
orderBy('a'), orderBy('b') · range on two fieldsyes
collection-group variants of the aboveyes (scope collectionGroup)

Requirements

  • IDX-1 Compile time: query() returns MissingCompositeIndex<fields> instead of a Query when the combination needs an undeclared composite, so getDocs/onSnapshot on it is a type error naming the fields (implemented and verified, §9).
  • IDX-2 Runtime, all modes: the same check runs before the request leaves; error missing-index includes the exact index to add.
  • IDX-3 icebase indexes check scans the code for queries and lists missing composites (CI-friendly).
  • IDX-4 firebase mode: generate and deploy firestore.indexes.json from the schema.
  • IDX-5 emulator/vm: every field that appears in a declared composite gets a column; each composite becomes a SQL index; single-field queries use per-field expression indexes created on demand (and listed in the console).
  • IDX-6 RTDB: orderByChild(x) requires x in the path's indexOn; .indexOn generated into database.rules.json.

8. Rules

  • RUL-1 firestore.rules, storage.rules, database.rules.json in exact Firebase syntax; deployed unchanged in firebase mode.
  • RUL-2 emulator/vm: IceBase evaluates rules itself: match blocks, wildcards, functions, request/resource, get()/exists()/getAfter(), list-query checks ("rules are not filters").
  • RUL-3 Conformance: the same rules test suite runs against IceBase and the official Firebase emulator; any difference is a bug.
  • RUL-4 Lint: field names used in rules must exist in the schema; comparisons are type-checked against field types.
  • RUL-5 Console playground: simulate a read/write as a chosen user against real data, in every mode.

9. Type safety (frontend + backend + functions)

The typings below are implemented as stubs and verified with tsc on an example project (0 errors).

// Frontend usage — reads exactly like Firebase, but everything is typed from icebase/schema.
import { addDoc, collection, getDocs, limit, onSnapshot, orderBy, query, serverTimestamp, where } from 'icebase/firestore';
import { signInWithEmailAndPassword } from 'icebase/auth';
import { httpsCallable } from 'icebase/functions';
import { auth, db, functions } from '../lib/icebase';
import { orders, products, users } from '../../icebase/schema';

// Single field: works on ANY schema field, no declaration (Firebase indexes single fields automatically).
export const byName = query(collection(db, products), where('name', '==', 'Boot'));
export const byEmail = query(collection(db, users), where('email', '==', 'a@b.c'));
export const newest = query(collection(db, products), orderBy('stock', 'desc'), limit(10));
// Equality on several fields: Firebase merges single-field indexes, so no composite needed.
export const activeShoes = query(collection(db, products), where('category', '==', 'shoes'), where('active', '==', true));

// Range + orderBy on the SAME field is still single-field.
export const midPrice = query(collection(db, products), where('priceCents', '>', 1000), orderBy('priceCents'));
// array-contains + orderBy → uses the declared composite ['tags contains', 'priceCents asc'].
export const tagged = query(collection(db, products), where('tags', 'array-contains', 'new'), orderBy('priceCents'));

// Composite: equality + orderBy on another field → needs the declared index ['category', 'priceCents asc'].
export async function cheapShoes() {
  const q = query(collection(db, products), where('category', '==', 'shoes'), orderBy('priceCents', 'asc'), limit(20));
  const snap = await getDocs(q);
  return snap.docs.map((d) => d.data().name);          // d.data() is { name: string; priceCents: number; … }
}

export function watchMyOrders(uid: string, cb: (n: number) => void) {
  // 'users/{uid}/orders' → collection(db, orders, uid). Uses the declared composite ['status', 'createdAt desc'].
  return onSnapshot(query(collection(db, orders, uid), where('status', '==', 'pending'), orderBy('createdAt', 'desc')), (s) => cb(s.size));
}

export async function placeOrder(uid: string) {
  await signInWithEmailAndPassword(auth, 'a@b.c', 'pw');
  await addDoc(collection(db, orders, uid), { status: 'pending', items: [], totalCents: 1200, createdAt: serverTimestamp() });
}

export const cancelOrder = httpsCallable<{ orderId: string }, { ok: true }>(functions, 'cancelOrder');

Cloud Firestore — 280 APIs · 7 console screens · Phase 1 (suggested)

Document database. The heart of IceBase: schema-based, composite-index-checked, Firebase rules.

  • FIREST-1 Every collection is declared with a schema (fields + types); reads return typed docs, writes are type-checked and validated at runtime before they leave

// icebase/schema — explicit schema + explicit indexes. The only place data shape is declared.
// Indexed fields become real columns in SQLite/Postgres; the whole document lives in one JSONB column.

export interface Timestamp { readonly seconds: number; readonly nanoseconds: number; toDate(): Date }
export interface DocumentReference<T = unknown> { readonly id: string; readonly path: string; readonly __doc?: T }

export interface Field<T> { readonly kind: string; readonly optional: boolean; readonly __t?: T }

type FieldMap = Record<string, Field<any>>;
type Req<S extends FieldMap> = { [K in keyof S as S[K] extends Field<infer T> ? (undefined extends T ? never : K) : never]: S[K] extends Field<infer T> ? T : never };
type Opt<S extends FieldMap> = { [K in keyof S as S[K] extends Field<infer T> ? (undefined extends T ? K : never) : never]?: S[K] extends Field<infer T> ? Exclude<T, undefined> : never };
type Flat<T> = { [K in keyof T]: T[K] } & {};
/** The TypeScript type of a document, inferred from its field map. */
export type Infer<S extends FieldMap> = Flat<Req<S> & Opt<S>>;

export declare const f: {
  string(opts?: { min?: number; max?: number }): Field<string>;
  number(opts?: { int?: boolean; min?: number; max?: number }): Field<number>;
  boolean(): Field<boolean>;
  timestamp(): Field<Timestamp>;
  enum<const E extends readonly string[]>(values: E): Field<E[number]>;
  array<T>(of: Field<T>, opts?: { max?: number }): Field<T[]>;
  map<S extends FieldMap>(fields: S): Field<Infer<S>>;
  ref<C extends AnyCollection>(to: C): Field<DocumentReference<DocOf<C>>>;
  geopoint(): Field<{ latitude: number; longitude: number }>;
  optional<T>(field: Field<T>): Field<T | undefined>;
};

/** "createdAt desc", "tags contains" … one entry per field in a composite index. */
export type IndexEntry<K extends string> = K | `${K} asc` | `${K} desc` | `${K} contains`;
export type FieldOf<E> = E extends `${infer K} ${'asc' | 'desc' | 'contains'}` ? K : E;

/** One declared composite index = the set of fields it covers (order/direction checked at runtime). */
export interface CompositeIndex<F extends string> { readonly f: F }
type IndexSetOf<I> = I extends readonly (infer E)[] ? (E extends readonly string[] ? CompositeIndex<FieldOf<E[number]>> : never) : never;

export interface Collection<P extends string, T, IX> {
  readonly path: P;
  readonly indexes: readonly (readonly string[])[];
  readonly __doc?: T;
  /** Union of declared composite indexes, e.g. CompositeIndex<'category' | 'priceCents'> | CompositeIndex<'active' | 'stock'> */
  readonly __ix?: IX;
}
export type AnyCollection = Collection<string, any, any>;
export type DocOf<C> = C extends Collection<string, infer T, any> ? T : never;
export type IndexesOf<C> = C extends Collection<string, any, infer IX> ? IX : never;

/** Declare a collection. `path` may contain {params} for subcollections: 'users/{uid}/orders'.
 *  `indexes` lists COMPOSITE indexes only — single-field indexes are automatic (like Firebase).
 *  Every index entry must name a declared field — a typo is a compile error. */
export declare function collection<
  const P extends string,
  S extends FieldMap,
  const I extends readonly (readonly IndexEntry<keyof S & string>[])[],
>(path: P, def: { fields: S; indexes: I; noIndex?: readonly (keyof S & string)[]; ttl?: keyof S & string }): Collection<P, Infer<S>, IndexSetOf<I>>;

export interface Schema<C extends Record<string, AnyCollection>> { readonly collections: C }
export declare function defineSchema<const C extends Record<string, AnyCollection>>(collections: C): Schema<C>;
