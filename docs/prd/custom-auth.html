Custom auth — no vendor lock-in

IceBase PRD addendum · ORCH-26 · from Panth's answer, 2026-10-24 · reference implementation: VardayiniDairy ~/Dev/VDP/backend/functions/src/ (challenge.ts, limits.ts, policy-limits.ts, whatsapp.ts, email.ts, sessions.ts, auth endpoints in index.ts)

1. Goal

  • Even with auth on firebase mode, the login process can be taken over by IceBase: your own SMTP, your own WhatsApp account / SMS gateway, your own Google OAuth client, your own message templates.
  • Firebase Auth is still used for what comes after login: user records, ID tokens / JWT, refresh, custom claims, request.auth in rules. IceBase signs in by minting a Firebase custom token.
  • App code does not change: frontend and backend call the same Firebase API names. The project config decides which sign-in method is native and which is custom.
  • End to end, not a kit: IceBase ships the endpoints, the challenge store, rate limits, blocks, approval page and default templates. The developer only provides credentials (or, optionally, their own send handler).
  • The same custom flows run unchanged in emulator mode (senders can be pointed at a local outbox shown in the console).

2. Config

// icebase.config.ts
import { defineConfig, senders } from 'icebase/config';

export default defineConfig({
  auth: {
    providers: ['password', 'emailLink', 'phone', 'google'],

    // Any method listed here is taken over by IceBase. The rest stay native Firebase.
    custom: {
      email: {
        // What is sent: sign-in (link or approval), password reset, email verification.
        sender: senders.smtp({ urlEnv: 'SMTP_URL', from: 'Acme <no-reply@acme.com>' }),
        // or: sender: senders.resend({ apiKeyEnv: 'RESEND_KEY', from: … })
        // or: sender: { handler: 'auth/sendEmail' }   ← your own function, see §5
        signIn: 'approval',              // 'approval' (VDP style, cross-device) | 'link' | 'code'
        templates: 'icebase/auth/templates', // optional overrides: signin.html, reset.html, verify.html (+ .txt)
      },
      phone: {
        sender: senders.whatsappCloud({ tokenEnv: 'WA_TOKEN', phoneNumberIdEnv: 'WA_PHONE_ID', template: 'otp_login', language: 'en' }),
        // or: senders.twilio({ … }) · senders.msg91({ … }) · { handler: 'auth/sendPhoneCode' }
        codeLength: 6,
      },
      google: {
        clientIdEnv: 'GOOGLE_CLIENT_ID',
        clientSecretEnv: 'GOOGLE_CLIENT_SECRET',
        // redirect URI is served by IceBase: https://<app>/__/icebase/auth/google/callback
      },
      // The security layer, shared by every custom method.
      security: {
        store: { database: 'default', path: '_icebase/auth' }, // Realtime Database instance + root path
        limits: {
          perIdentifier: { perHour: 5, perDay: 20 },  // one email / phone
          perIp: { perHour: 30 },
          global: { phoneSendsPerDay: 2000 },          // spend cap on paid channels
        },
        challenge: { ttlMinutes: 10, maxAttempts: 5 },
        blockMinutes: 5,                               // "this wasn't me" on the approval page
        allow: { emailDomains: ['*'], phoneCountries: ['IN', 'US'] },
      },
    },
  },
});

Secrets are env-var names, as everywhere in IceBase. icebase deploy refuses to deploy a custom method whose env vars are missing.

4. What IceBase ships (end to end)

  1. Auth endpoints — one HTTPS function icebaseAuth generated and deployed by icebase deploy (firebase mode: Cloud Functions; emulator: the local server), routes /email/start|collect|approve|reject|page, /phone/start|verify, /google/start|callback, /reset/start|confirm, /verify/start|confirm. Hosting gets a /__/icebase/auth/** rewrite.
  2. Challenge store in RTDB at security.store.path: secrets stored only as SHA-256, compared in constant time, single use, TTL, max attempts; public status node split from the secret node (VDP signin/{id} vs …/challenge/state). Database rules for the path are generated and merged into database.rules.json (secret nodes: no client access).
  3. Three secrets for approval mode: approvalToken (in the mail; can only approve), clientSecret (only in the starting tab; can only collect), code (phone only). The custom token never travels through the email.
  4. Rate limiting + blocks in RTDB: per identifier (hashed in the path), per IP, global spend cap on paid channels; counters via atomic increment; "this wasn't me" blocks the device signature for blockMinutes.
  5. Approval page served by IceBase: names the device and the site being signed into; approve / reject.
  6. Default templates (HTML + text) for sign-in, reset, verify, and WhatsApp authentication template guidance; overridable per file.
  7. Senders: smtp, resend, whatsappCloud, twilio, msg91, console (emulator: shown in the IceBase console outbox), or your own handler.
  8. User linking: custom sign-ins create/find Firebase users with stable uids; email and phone are written onto the Firebase user (emailVerified true after proof), so rules and Admin APIs see the same thing as native sign-in.
  9. Audit trail of starts / failures / blocks under the store path, with TTL cleanup (scheduled function), visible in the console later.

5. Own handler (optional)

// icebase/functions/src/auth.ts — only if you want full control over sending
import { defineEmailSender, definePhoneSender } from 'icebase/auth/server';

export const sendEmail = defineEmailSender(async (m) => {
  // m.kind: 'signIn' | 'passwordReset' | 'verifyEmail'
  // m.to, m.link (approval/sign-in/reset URL), m.code?, m.device, m.site, m.rendered { subject, html, text }
  await myMailer.send({ to: m.to, subject: m.rendered.subject, html: m.rendered.html });
});

export const sendPhoneCode = definePhoneSender(async (m) => {
  // m.to (E.164), m.code, m.site
  await myWhatsApp.sendTemplate(m.to, 'otp_login', [m.code]);
});

Two handlers are all a developer ever writes, and only when the built-in senders don't fit. Everything else (challenges, limits, tokens, pages) stays IceBase's.

6. Acceptance

  • An app with auth.mode = firebase and custom.email + custom.phone + custom.google signs in with no Firebase email/SMS ever sent; request.auth.uid in Firestore rules is the same uid as before the switch.
  • Removing custom.email from the config falls back to native Firebase email with no app code change.
  • Rate limit, attempt cap, TTL and block behave as configured (tests for each), in firebase and emulator mode.
  • Secrets never readable by a client (rules tests on the store path).

7. Who a user is, Sign in with Apple, hosted sign-in for many apps (0.7.0)

OCZ-112, approved by Panth 2026-11-12: a hosted login site (one Firebase project) that signs people into many apps. Every piece works in firebase and emulator mode.

7.1 newUserUid and signInClaims

HookWhat it does
newUserUid(identity)
identity: { email?, phone?, google?, apple? }		The uid of a user custom auth is about to create (email, phone, Google, Apple): createUser({ uid, … }). Lookup order stays: identity link → by email / phone → newUserUid → create. If a user with that uid already exists (auth/uid-already-exists, or getUser finds it) it is that user, and the verified email / phone is set on it — for accounts an older system made with a uid derived from the email and no email on the record. Return undefined to let Firebase pick.
signInClaims(user, { method, client?, sid? })
method: 'email' | 'phone' | 'google' | 'apple' | 'sso'		Merged into every custom token custom auth mints (createCustomToken(uid, claims)), so they are in the ID token — e.g. { role: 'authenticated', email } for Supabase's third-party auth.
// functions source (config.functions.source) — icebase deploy and icebase dev pass these to the handler
export const newUserUid = ({ email }) => (email ? uuidv5(email, NAMESPACE) : undefined);
export const signInClaims = (user) => ({ role: 'authenticated', email: user.email ?? null });
// or: createAuthHandler(config, env, { newUserUid, signInClaims }) / icebaseAuth(config, env, { … })

7.2 Sign in with Apple

custom: {
  apple: {
    clientIdEnv: 'APPLE_SERVICES_ID',   // web flow (Services ID); also an accepted audience
    teamIdEnv: 'APPLE_TEAM_ID',
    keyIdEnv: 'APPLE_KEY_ID',
    privateKeyEnv: 'APPLE_PRIVATE_KEY', // the .p8, PEM (newlines may be escaped as \n)
    audiences: ['com.acme.app'],        // native bundle ids /apple/token accepts
  },
}
RouteWhat happens
GET /apple/start?return=&mode=popup|redirectThe return URL is checked like Google's; state + nonce stored under oauth/; 302 to appleid.apple.com/auth/authorize (response_type=code, response_mode=form_post, scope=name email).
POST /apple/callbackApple's form post (Origin https://appleid.apple.com, so it skips the origin check). The code is exchanged at /auth/token with client_secret = an ES256 JWT (iss team, sub client id, aud appleid.apple.com, kid, 5 minutes); id_token claims checked (iss, aud, exp, nonce). User: link identities/apple/<sha(sub)> → verified email → newUserUid → create; the name (the user field, first time only) becomes displayName. Delivered like Google: popup postMessage({ icebase: 'apple', token }), redirect #icebase_token=.
POST /apple/token { idToken, name?, nonce? }A native app's identity token: RS256 signature checked against appleid.apple.com/auth/keys (cached an hour), iss, exp, aud ∈ audiences ∪ {client id} → { token }.

Client: signInWithPopup / signInWithRedirect(auth, new OAuthProvider('apple.com')) go to this flow when auth.custom.apple is set; getRedirectResult picks it up; signInWithAppleIdToken(auth, idToken, name?) for native apps. createAuthHandler({ fetch }) replaces the fetch used to reach Google and Apple (tests).

7.3 Hosted sign-in for many apps (SSO, authorization code + PKCE)

custom: {
  sso: {
    loginUrl: 'https://auth.acme.com/',  // /sso/authorize redirects to loginUrl?sso=<request>
    clients: {
      shop: { name: 'Acme Shop', redirectUris: ['https://shop.acme.com/sso', 'com.acme.shop://*'], iconUrl: 'https://…/shop.png' },
    },
  },
}
RouteWhat happens
GET /sso/authorize?client_id&redirect_uri&state&code_challenge&code_challenge_method=S256Unknown client, redirect URI not registered (exact; an entry ending in * by prefix; custom schemes allowed) or no S256 challenge → an HTML error page, never a redirect. Else the request is stored (sso/req/<rid>, challenge TTL) and 302 to loginUrl?sso=<rid>.
POST /sso/request { sso }{ client: { id, name, iconUrl? }, expiresAt } — the hosted page's "Continue to <name>".
POST /sso/grant { sso, idToken }The hosted page's user (ID token, checkRevoked) → a session sessions/<uid>/<sid> { client, clientName, device, ip, createdAt, lastSeenAt, revoked } → a one-time code (stored as SHA-256 under sso/code/, 5 minutes, single use, bound to client, redirect URI, challenge, uid, sid) → { redirect: redirect_uri?code=…&state=… }.
POST /sso/deny { sso }{ redirect: redirect_uri?error=access_denied&state=… }
POST /sso/token { code, code_verifier, client_id, redirect_uri }Claimed in a transaction (single use, a wrong verifier burns it too); every binding must match, S256(verifier) = challenge, session not revoked → { token, uid, sid }, the token carrying signInClaims(user, { method: 'sso', client, sid }) + sid + client.
POST /sso/ping { idToken }The token's sid: live → lastSeenAt, { ok: true }; revoked, gone, or the account's tokens revoked → { revoked: true }.
POST /sso/sessions { idToken }The caller's sessions newest first (current marks the token's own) and apps: one per client with live sessions { client, clientName, iconUrl, sessions (count), lastSeenAt }.
POST /sso/revoke { idToken, sid | client | all }Marks the caller's matching sessions revoked (revokedAt); all also revokes every refresh token.

Every /sso/* POST answers CORS for any origin: no cookies ride on them, the code is protected by PKCE and the rest by the ID token. Every other route keeps the authorized-domain origin rule. Database rules: sessions/$uid/$sid/revoked is readable by $uid (an app may listen for its revocation); the rest of the store stays closed. Admin: getAuthSecurity(app).listSessions(uid), .revokeSession(uid, sid); cleanup() also drops expired requests and codes.

Client (@panth977/icebase/auth)
startSsoSignIn(auth, { clientId, redirectUri, open? })Verifier + state (kept in localStorage as icebase:sso:<state>), then open(url) or location.assign(url). ssoAuthorizeUrl(auth, { clientId, redirectUri }) only builds { url, state, verifier }.
completeSsoSignIn(auth, url?, pending?)On the redirect URI: exchanges the code and signs in; null when the URL is not an SSO return; throws auth/user-cancelled (access_denied) or auth/invalid-sso-state.
watchSsoSession(auth, onRevoked?)Pings on start, when the page becomes visible and every 10 minutes; once revoked, signs out and calls onRevoked.
Hosted page: getSsoRequest, grantSsoRequest (→ redirect URL), denySsoRequest, listSsoSessions, revokeSsoSessions(auth, { sid } | { client } | { all: true })
