Custom auth — no vendor lock-in

IceBase PRD addendum · ORCH-26 · from Panth's answer, 2026-10-24 · reference implementation: VardayiniDairy ~/Dev/VDP/backend/functions/src/ (challenge.ts, limits.ts, policy-limits.ts, whatsapp.ts, email.ts, sessions.ts, auth endpoints in index.ts)

1. Goal

  • Even with auth on firebase mode, the login process can be taken over by IceBase: your own SMTP, your own WhatsApp account / SMS gateway, your own Google OAuth client, your own message templates.
  • Firebase Auth is still used for what comes after login: user records, ID tokens / JWT, refresh, custom claims, request.auth in rules. IceBase signs in by minting a Firebase custom token.
  • App code does not change: frontend and backend call the same Firebase API names. The project config decides which sign-in method is native and which is custom.
  • End to end, not a kit: IceBase ships the endpoints, the challenge store, rate limits, blocks, approval page and default templates. The developer only provides credentials (or, optionally, their own send handler).
  • The same custom flows run unchanged in emulator mode (senders can be pointed at a local outbox shown in the console).

2. Config

// icebase.config.ts
import { defineConfig, senders } from 'icebase/config';

export default defineConfig({
  auth: {
    providers: ['password', 'emailLink', 'phone', 'google'],

    // Any method listed here is taken over by IceBase. The rest stay native Firebase.
    custom: {
      email: {
        // What is sent: sign-in (link or approval), password reset, email verification.
        sender: senders.smtp({ urlEnv: 'SMTP_URL', from: 'Acme <no-reply@acme.com>' }),
        // or: sender: senders.resend({ apiKeyEnv: 'RESEND_KEY', from: … })
        // or: sender: { handler: 'auth/sendEmail' }   ← your own function, see §5
        signIn: 'approval',              // 'approval' (VDP style, cross-device) | 'link' | 'code'
        templates: 'icebase/auth/templates', // optional overrides: signin.html, reset.html, verify.html (+ .txt)
      },
      phone: {
        sender: senders.whatsappCloud({ tokenEnv: 'WA_TOKEN', phoneNumberIdEnv: 'WA_PHONE_ID', template: 'otp_login', language: 'en' }),
        // or: senders.twilio({ … }) · senders.msg91({ … }) · { handler: 'auth/sendPhoneCode' }
        codeLength: 6,
      },
      google: {
        clientIdEnv: 'GOOGLE_CLIENT_ID',
        clientSecretEnv: 'GOOGLE_CLIENT_SECRET',
        // redirect URI is served by IceBase: https://<app>/__/icebase/auth/google/callback
      },
      // The security layer, shared by every custom method.
      security: {
        store: { database: 'default', path: '_icebase/auth' }, // Realtime Database instance + root path
        limits: {
          perIdentifier: { perHour: 5, perDay: 20 },  // one email / phone
          perIp: { perHour: 30 },
          global: { phoneSendsPerDay: 2000 },          // spend cap on paid channels
        },
        challenge: { ttlMinutes: 10, maxAttempts: 5 },
        blockMinutes: 5,                               // "this wasn't me" on the approval page
        allow: { emailDomains: ['*'], phoneCountries: ['IN', 'US'] },
      },
    },
  },
});

Secrets are env-var names, as everywhere in IceBase. icebase deploy refuses to deploy a custom method whose env vars are missing.

4. What IceBase ships (end to end)

  1. Auth endpoints — one HTTPS function icebaseAuth generated and deployed by icebase deploy (firebase mode: Cloud Functions; emulator: the local server), routes /email/start|collect|approve|reject|page, /phone/start|verify, /google/start|callback, /reset/start|confirm, /verify/start|confirm. Hosting gets a /__/icebase/auth/** rewrite.
  2. Challenge store in RTDB at security.store.path: secrets stored only as SHA-256, compared in constant time, single use, TTL, max attempts; public status node split from the secret node (VDP signin/{id} vs …/challenge/state). Database rules for the path are generated and merged into database.rules.json (secret nodes: no client access).
  3. Three secrets for approval mode: approvalToken (in the mail; can only approve), clientSecret (only in the starting tab; can only collect), code (phone only). The custom token never travels through the email.
  4. Rate limiting + blocks in RTDB: per identifier (hashed in the path), per IP, global spend cap on paid channels; counters via atomic increment; "this wasn't me" blocks the device signature for blockMinutes.
  5. Approval page served by IceBase: names the device and the site being signed into; approve / reject.
  6. Default templates (HTML + text) for sign-in, reset, verify, and WhatsApp authentication template guidance; overridable per file.
  7. Senders: smtp, resend, whatsappCloud, twilio, msg91, console (emulator: shown in the IceBase console outbox), or your own handler.
  8. User linking: custom sign-ins create/find Firebase users with stable uids; email and phone are written onto the Firebase user (emailVerified true after proof), so rules and Admin APIs see the same thing as native sign-in.
  9. Audit trail of starts / failures / blocks under the store path, with TTL cleanup (scheduled function), visible in the console later.

5. Own handler (optional)

// icebase/functions/src/auth.ts — only if you want full control over sending
import { defineEmailSender, definePhoneSender } from 'icebase/auth/server';

export const sendEmail = defineEmailSender(async (m) => {
  // m.kind: 'signIn' | 'passwordReset' | 'verifyEmail'
  // m.to, m.link (approval/sign-in/reset URL), m.code?, m.device, m.site, m.rendered { subject, html, text }
  await myMailer.send({ to: m.to, subject: m.rendered.subject, html: m.rendered.html });
});

export const sendPhoneCode = definePhoneSender(async (m) => {
  // m.to (E.164), m.code, m.site
  await myWhatsApp.sendTemplate(m.to, 'otp_login', [m.code]);
});

Two handlers are all a developer ever writes, and only when the built-in senders don't fit. Everything else (challenges, limits, tokens, pages) stays IceBase's.

6. Acceptance

  • An app with auth.mode = firebase and custom.email + custom.phone + custom.google signs in with no Firebase email/SMS ever sent; request.auth.uid in Firestore rules is the same uid as before the switch.
  • Removing custom.email from the config falls back to native Firebase email with no app code change.
  • Rate limit, attempt cap, TTL and block behave as configured (tests for each), in firebase and emulator mode.
  • Secrets never readable by a client (rules tests on the store path).
